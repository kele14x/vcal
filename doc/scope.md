# Scope

This is the **mutable working state**: what works today, what's still planned, and known issues. Agents update this file first when scope changes or a task completes — collapse completed features to one-line summaries; git history is the granular record.

For the long-term LRM-coverage target, see [lrm-coverage.md](lrm-coverage.md).

Priority key: **P0** critical or blocking; **P1** important; **P2** non-blocking and deferrable (may remain unimplemented). No P0 items are currently documented.

## What works

- REPL shell with `rustyline` history
- Output byte policy: `$display` / `$write` and formatted `display_expression` output is a raw byte stream everywhere (pipes, files, Unix terminals stay byte-exact); a Windows console degrades non-UTF-8 bytes to lossy UTF-8 instead of erroring (see [repl.md](repl.md))
- Unified non-empty `display_expression` echo lists (see [non-standard.md](non-standard.md)): every top-level expression input is a display-expression argument list, so `a` retains canonical calculator output, `a, b` echoes both values canonically, null comma slots emit one space each like `$display`, and a leading string-style expression such as `"a=%d", a` uses the `$display` format-control engine while rendering arguments left unconsumed by format controls canonically; trailing `;` suppresses the whole echo
- Integer and real literals, all LRM forms (LRM 3.5.2)
- String literals as packed unsigned 8-bit vectors (LRM 3.6 / A.8.8), with friendly escaped display for bare strings and string-only concatenation / replication; the formatter shared by `$display` / `$write` and formatted `display_expression` supports basic format strings, null arguments, and raw-byte output; internal zero-width numeric display renders with one `0` digit
- All operators between integers (see [operators.md](operators.md))
- Integer `**` evaluates its exponent as a self-determined expression and uses width-bounded modular exponentiation, so nested or very large exponents wrap correctly without unbounded intermediates
- Real arithmetic and mixed integer/real promotion (LRM 5.1.5 / 5.1.7 / Tables 5-2, 5-3)
- Two-pass context (width, signedness) propagation; leftmost-base propagation; `reg` display base starts as a weak binary fallback and resolves from the first whole-reg integer init/assignment
- `reg` / `integer` / `real` declarations and blocking assignment with the full LRM A.8.5 `variable_lvalue` — bare name, bit/part/indexed-part selects, and arbitrarily nested concatenations on the LHS (see [variables.md](variables.md))
- 1-D unpacked arrays on `reg` / `integer` / `real` (LRM 4.9 / A.2.2.1); arrays are capped at 65,536 elements, and vector-array payload is additionally capped at the same 16,777,216-bit limit as scalar vectors
- Static-semantic validation as a top-level pre-pass over every expression entry and every display argument list — errors prefixed `Syntax error:` (lex/parse) or `Semantic error:` (static semantics), the latter including display format-control rejections
- Error diagnostics preserve side effects: `$display` / `$write` bytes from statements that completed earlier in the same input are emitted ahead of the diagnostic, while the failing statement and every later one do not run and no value is echoed (see [repl.md](repl.md))
- System tasks: `$finish`, `$stop` (LRM 17.4), `$display` / `$write` and the `b`/`o`/`h` suffixed variants `$displayb` / `$displayo` / `$displayh` / `$writeb` / `$writeo` / `$writeh` (LRM 17.1 display family, basic formatting subset including `%b`/`%o`/`%d`/`%h`/`%s`/`%c`/real controls). Suffixed variants default the unformatted-integer base to binary / octal / hex respectively; explicit format controls still override. All system tasks accept null arguments (empty comma slots); `$display`/`$write` family emit one space per null for a supported format control (the control is validated first, so an unsupported one still errors), `$finish`/`$stop` discard them. LRM display controls outside this subset are intentionally unsupported for now, including `%u`, `%z`, `%t`, `%m`, strength formats, and field-width / precision modifiers.
- System functions:
  - Sign casts (LRM 5.5): `$signed`, `$unsigned`
  - Real conversions (LRM 17.7.1 / §3.5.3): `$rtoi`, `$itor`, `$realtobits`, `$bitstoreal`
  - Math (LRM 17.11): `$clog2` plus 21 real-math functions (`$ln`/`$log10`/`$exp`/`$sqrt`/`$pow`/`$floor`/`$ceil`, the trig and hyperbolic family, `$atan2`/`$hypot`)
  - Display-base casts (vcal-specific): `$bin`, `$oct`, `$dec`, `$hex` — see [non-standard.md](non-standard.md)

## Active scope

Planned but not yet implemented:

- **[P1] Multi-line edit.** The REPL accepts only single-line input today; the right TUI affordance for multi-line editing is still being explored.

## Known issues

Review 2026-09-22 identified no P0 issue: all 750 tests and 96 recursion stress cases passed on macOS, and additional malformed-input / mixed-nesting probes reproduced no stack overflow under default settings. This is bounded review evidence, not a guarantee that no P0 exists; interactive and Windows paths were not exercised. Select parsing still recurses behind its 64-level cap, and raising the parse-only AST display depth retains the documented recursive-rendering risk.

- **[P1] Nested part-select bounds cause exponential re-evaluation — confirmed 2026-09-22.** `select_meta_width` (`src/eval.rs:4699`) resolves bounds through `evaluate_constant_expr` (`:868`), re-entering annotation, validation, and evaluation; select validation (`:1184`) repeats that work. Python generator: `"reg [0:0] r=0; " + "r[0:"*n + "0" + "]"*n`. Local release-build medians at depths 8 / 10 / 11 were 0.023 / 0.274 / 1.00 s; depth 12 exceeded a 3-second timeout despite the one-bit result. Parsing 64 levels alone took about 5 ms. Nested indexed-select widths have the same issue, so the parser's 64-level cap does not bound evaluation cost adequately. Resolve and retain select operand annotations and bound/width values within each evaluation instead of repeatedly starting the full pipeline; add nested-bound and indexed-width regressions, not just nested bit-selects.

- **[P1] LRM-reserved keywords are usable as ordinary identifiers.** `reg if`, `reg while`, `reg module`, `reg always`, `reg case`, `reg endmodule`, `reg begin`, `reg input`, `reg output`, `reg wire` (and many more from LRM 3.6.4) all succeed silently; `if = 5; if` then evaluates. Only the words the parser actively consumes — `reg`, `signed`, `integer`, `real` — are reserved. Harmless today because there's no control flow, but a snippet pasted from a module will bind names the user did not intend. Fix: lift the LRM 3.6.4 reserved-word list into the lexer and reject any of them in identifier position.

- **[P2] Nested replication counts incur cubic work — confirmed 2026-09-22.** Replication annotation validates and evaluates the whole count subtree (`src/eval.rs:548`, `:564`), while validation separately evaluates descendant counts (`:1298`, `:3984`). Python generator: `"{"*n + "1'b1" + "{1'b1}}"*n`. Every intermediate result remains one bit, but local release-build medians at depths 80 / 160 / 320 were 0.018 / 0.109 / 0.812 s; depth 640 (about 5 KB of input) exceeded 3 seconds, while parse-only took about 4 ms. Retain validated count results within each evaluation rather than re-walking their subtrees; add count-position nesting regressions alongside the existing replication-body stress cases.

- **[P2] Comments between a literal's base and digits are rejected — confirmed 2026-09-22.** `8/*comment*/'d5` succeeds, but `8'd/*comment*/5` and `'h /*comment*/ ff` fail with `Syntax error: missing digits in integer literal`. `read_base_marker_and_digits` (`src/lexer.rs:543`) treats `/` as a delimiter before reading any value digits instead of skipping the comment. This is inconsistent with the documented comment-separator rule in [repl.md](repl.md); Verilator accepts these forms, while Icarus also rejects them. Handle comments between the base token and the first value digit without joining digit runs separated by comments.

- **[P2] Assignments copy unrelated session data — reconfirmed 2026-09-15.** Declarations, successful integer/vector and real assignments, and valid real-array element writes deep-clone the entire variable map for atomic updates, including unrelated arrays. A fresh local release-build probe of 200 scalar assignments measured five-run medians of 0.0062 s without an array versus 0.282 s with `reg [255:0] bulk [0:65535]` (including process startup and declarations). This is a performance issue, not a correctness bug. Stage only affected bindings / elements while preserving statement atomicity and resolving RHS values and LHS indices against the original session.

- **[P2] Malformed real literals produce misleading diagnostics.** Literals like `1._0` or `9.` surface as `invalid decimal digits: 1.0` after the underscore-strip / digit-strip step, because the lexer's `real_after_dot` lookahead requires `.` followed by a digit and otherwise falls through to the integer path. The diagnostic is correct in spirit (the literal is not a valid real) but the message is misleading. A future pass should recognize "digit-run + `.`" as a real-literal commitment and emit a real-specific error.

- **[P2] The stage-prefix invariant is enforced by convention, not structure.** `evaluate_expr` (`src/eval.rs:811`, `:813`) and `evaluate_assignment_rhs` (`src/eval.rs:848`, `:859`) prefix the annotate and validate steps with `Semantic error:` but return the evaluate step's `Err` verbatim, so any error raised there reaches the REPL with no prefix. Candidate sites inside that phase are the replication-count checks (`src/eval.rs:3326`, `:3330`, `:3337`), the real-as-integer leaf rejection (`src/eval.rs:1650`), and `require_vector` (`src/lib.rs:109`, `:111`). Latent rather than observable: no input found so far reaches them, because the validator rejects the same cases first. Contrast the *deliberately* unprefixed helpers, which document that callers add the prefix — `evaluate_constant_expr` (`:874`), `evaluate_subexpr_as_integer` (`:887`), `replication_count_value` (`:3984`). Fix: replace the internal `Result<_, String>` with a typed `StageError` (`Syntax` / `Semantic`, later `Runtime`) and render the prefix exactly once at the sole convergence point (`src/lib.rs:374`, `:384`). This makes classification a compile-time obligation on whoever raises the error — the person who still knows which stage they are in — instead of a guess made at the boundary, and it retires the "caller must prefix" helpers as a concept. Cost: ~111 signatures across `eval.rs` (51), `parser.rs` (23), `lib.rs` (17), `lexer.rs` (11), `system_call.rs` (8), `value.rs` (1), plus deleting the 15 hand-written prefix sites. Must be migrated wholesale — a partial migration keeps two conventions alive with `From`-style conversions at the seams, which is worse than either endpoint. The public contract is unchanged either way (`EvalError.message` stays a `String`). **Deferred until a genuine second error category lands** (file I/O, `$fopen`, anything whose success is only known at execution time): until then the enum defends a property with zero observed violations. A lighter alternative — defaulting any unprefixed message to `Semantic error:` at `src/lib.rs:384` behind a `debug_assert!` — was considered and rejected: it either guesses wrong once a runtime category exists, or it substitutes runtime self-audit for what the tests should guarantee.
